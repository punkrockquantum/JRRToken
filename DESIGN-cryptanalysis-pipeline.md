# Optimal architecture for producing a cryptanalytic result

**Status:** design, not built. Written 2026-09-24 as the successor to `algebraic-probe/`.

`algebraic-probe` is a measurement instrument with strong provenance discipline
and no cryptanalytic output. It will not produce one: its exhaustive arms cap at
2^18–2^26 in pure Python, its Tier S promotion path is closed by its own
pre-registration, and its target is the most heavily analysed hash function in
existence. More cycles of it do not converge on anything.

This document specifies what a pipeline aimed at an actual result looks like. It
is a different machine. The epistemic layer is the only part worth carrying over.

---

## 0. The three decisions that determine everything

Almost all of the outcome is fixed before a line is written.

**Decision 1 — target class.** Not SHA-256. Twenty-plus years and hundreds of
researcher-years stand between you and a marginal improvement; the best published
preimage attacks reach roughly two-thirds of its rounds and each further round
has cost a paper. The marginal return on another instrument pointed at it is
approximately zero.

Point it instead at **arithmetisation-oriented (AO) primitives** — the
Poseidon/Poseidon2, Rescue-Prime, Griffin, Anemoi, MiMC families used inside
zero-knowledge proof systems. Four properties make them the right target:

- Their security arguments rest on *conjectures about solver behaviour* — "a
  Gröbner basis computation on this system is infeasible because its degree of
  regularity is D". That is an empirical claim about a program, and an
  experiment factory can test it.
- Parameter sets are frequently generated by scripts, in bulk, and many are
  deployed without individual analysis.
- Several have been weakened or broken within months of publication, so the
  literature actively disagrees with itself — which is the condition under which
  a careful measurement changes someone's mind.
- Instances are small enough that a real solver can close them exactly.

**Decision 2 — method.** Solver-driven, not enumeration-driven. The work is
*translating a primitive into a constraint system*; the search is delegated to
mature solvers. Writing your own search is the single most common way these
projects die.

**Decision 3 — you never write a solver.** msolve, Magma, Singular for Gröbner;
CaDiCaL/Kissat/CryptoMiniSat for SAT; Gurobi/SCIP/CBC for MILP. Your code
generates models and interprets answers. Nothing else.

*Note on citations: the technique names above (MILP-modelled division property,
monomial prediction, automated MITM search, Gröbner-based AO attacks) are stated
from background knowledge. Every specific numeric claim attributed to a paper
must be transcribed from the primary source before it enters a calibration case
— the same rule that holds `algebraic-probe`'s E-04 open.*

## 1. Layer architecture

Six layers, each with one job and a hard boundary. The boundaries are where the
failure modes live, so each is stated with the check that enforces it.

```
  L0  Primitive specification   one declarative source of truth
  L1  Model compilers           spec -> polynomial system / CNF / MILP
  L2  Solver adapters           delegate, pin, record
  L3  Experiment driver         parameter ladders, scaling measurement
  L4  Claim verification        re-check candidates against the reference
  L5  Provenance and epistemics ported from algebraic-probe
```

### L0 — Primitive specification

One declarative description per primitive, from which **everything** downstream
is generated: the reference implementation, the polynomial system, the CNF, the
MILP model.

This exists to kill the defect that silently invalidates most such projects: the
model and the implementation disagree, so the attack is against a cipher nobody
deployed. Generating both from one source makes divergence impossible rather
than unlikely.

**Enforcement:** the generated reference implementation must reproduce the
primitive's official test vectors. No test vectors, no primitive — a spec that
cannot be validated against its designers' own output is not admitted.

### L1 — Model compilers

`spec → F_p polynomial system` for Gröbner and univariate-reduction attacks.
`spec → CNF` for SAT-based differential, preimage and collision search.
`spec → MILP` for division property, monomial prediction and automated MITM.

**Enforcement — the round-trip test, which is the load-bearing check in the
whole design:** take any satisfying assignment the model produces, decode it,
and run it through the reference implementation. It must satisfy the original
relation. A model that passes this cannot be describing a different cipher.

Run it in the other direction too: take a known input/output pair from the
reference implementation, encode it, and assert the model accepts it. That
catches over-constrained models, which fail silently as "no attack found" and
are the reason a project can run for months and measure nothing.

### L2 — Solver adapters

A thin uniform interface over each solver, recording: solver name, exact
version, seed, parameters, wall-clock, peak memory, exit status, and — for
Gröbner — **the maximum degree reached and the largest matrix dimension**. That
last pair is the actual scientific observable for AO primitives, not the
wall-clock.

Two rules:

- **Prefer open solvers.** A result that only reproduces in Magma is a result
  most people cannot check. msolve, Kissat and SCIP keep the work checkable.
- **Every headline claim runs on two independent solvers.** Solver
  nondeterminism, heuristic differences and outright bugs are real; agreement
  between two unrelated implementations is the cheapest guard available.

### L3 — Experiment driver

You cannot solve the full parameter set. That is the premise, not a limitation.

So: run a **ladder** — rounds 1, 2, 3, … until the solver hits a wall — and
measure the observable at each rung. Then fit growth and extrapolate.

This is where the discipline carried over from `algebraic-probe` earns its keep,
because the extrapolation is the entire attack and it is **not a measurement**:

- Each solved rung is **Tier E** — exact, complete, reproducible.
- The fitted curve is **Tier S at best, and usually just a model.** It must
  never be reported in the same register as the rungs.
- Require **at least two growth models** (e.g. linear-in-rounds vs quadratic,
  or degree-of-regularity vs measured solving degree), report both, and report
  **the round count at which they diverge**. That divergence point is the honest
  boundary of what the experiment supports.

The wall itself is a result. "Rounds 1–7 solved exactly; round 8 exceeded 512 GB
at degree 14" is a publishable, checkable statement, and it is what most cells
will produce.

### L4 — Claim verification

Anything the pipeline calls an attack must survive a check that shares no code
with the thing that produced it:

- A preimage/collision candidate is **executed against the reference
  implementation**. Not against the model. Not against a decoder.
- A distinguisher is re-run on fresh random instances with the statistic
  computed by an independent path.
- **The cost gate:** data, time and memory are compared against the correct
  generic baseline *in the correct attack model*. A "break" that costs more than
  generic is structure, not an attack, and must be reported as structure.

This layer is where an instrument earns the right to use the word *attack*, and
it should be the hardest gate in the system to pass.

### L5 — Provenance and epistemics

Port wholesale from `algebraic-probe`, because the AO attack literature has a
genuine reproducibility problem and this is the part that addresses it directly:

- Tier labels assigned by code path; cross-tier arithmetic raises.
- Pre-registration of what counts as a break, written **before** the ladder runs.
- Append-only hash-chained result logs, with solver versions embedded.
- Mandatory blindness statements on every negative.
- Byte-identical regeneration of committed result tables.

That last point is the differentiator. In a field where disputes routinely take
the form "your experiment does not reproduce", a pipeline whose every number
regenerates byte-for-byte is not bureaucratic overhead — it is the product.

## 2. Where these projects actually die

Designed against explicitly, because each has killed real work:

| failure | design response |
|---|---|
| Model and implementation describe different ciphers | Both generated from L0; bidirectional round-trip test in L1 |
| Over-constrained model reports "no attack" forever | Reverse round-trip: a known-good pair must be *accepted* |
| Solver nondeterminism makes results unreproducible | Pin version and seed; every headline claim on two solvers |
| Extrapolating with the wrong curve shape | ≥2 growth models, both reported, divergence point stated |
| "Attack" that loses to generic | Mandatory cost gate against the right baseline and model |
| Result only reproduces under a commercial licence | Open solvers preferred; licensed ones corroborate, never carry |
| Gröbner memory explosion mid-run | Instrument degree and matrix size; stop cleanly; report the wall as data |
| Months of compute on a cell nobody cares about | Target-selection gate in §0 applied *before* any cell is scheduled |

## 3. What this environment is missing

Checked, not assumed — this container has **no sympy, no msolve, no Singular, no
Magma, no SAT solver, no MILP solver**. The tooling *is* the architecture, and
none of it is present.

Realistic prerequisites, in dependency order:

1. **msolve** (open, fast F4 over F_p) — the single highest-value install.
2. **A SAT solver** — CaDiCaL or Kissat.
3. **An MILP solver** — SCIP if open-only, Gurobi if a licence exists.
4. **SageMath** for field arithmetic and glue, or a careful pure-Python F_p layer
   if the dependency is unacceptable.
5. **Memory.** Gröbner on AO systems is memory-bound before it is time-bound.
   A machine with 128 GB+ decides how many rungs of the ladder you reach, and
   therefore how far the extrapolation can be anchored.

Without at least items 1 and 5, this architecture cannot run, and building the
surrounding layers first would repeat `algebraic-probe`'s mistake in a new
costume: excellent scaffolding around a measurement that cannot reach anything.

---

## 4. Honest expected value

- **Most cells will find nothing.** That is the normal outcome and, reported as a
  measured bound with a stated wall, it is still worth publishing.
- **The realistic win** is a deployed AO parameter set whose measured solving
  degree grows more slowly than its designers' conjecture, thinning the security
  margin below what was claimed. That is a real, citable result, and it is the
  kind this architecture is shaped to find.
- **Time to first meaningful output:** months, not days, and dominated by L0/L1
  correctness plus solver wall-time — not by writing code.
- **What it will not do** is break SHA-256, and no architecture on this budget
  will.

---

## 5. Build order

Deliberately front-loads the thing most likely to invalidate everything else.

1. **One primitive, end to end, smallest sensible parameters.** MiMC over a
   prime field is the right first target: simplest algebraic structure, existing
   literature to calibrate against, and `algebraic-probe` already has a MiMC
   implementation to cross-check L0 against.
2. **L0 + L1 + the round-trip tests.** Do not proceed until a model's solutions
   verify against the reference implementation in both directions.
3. **L2 with msolve, plus the degree/matrix-size instrumentation.**
4. **L3 ladder on MiMC**, reproducing a known degree-growth result. If the
   pipeline cannot reproduce something already published, it is not ready to
   claim something new — this is the calibration gate, and it is non-negotiable.
5. **L4 and L5**, before the first novel cell is scheduled, so that no result is
   ever produced outside the provenance discipline.
6. **Only then**, widen to Poseidon-family parameter sets.

Step 4 is the gate that separates this from its predecessor. `algebraic-probe`
could never reproduce a published result because it could not reach one; this
pipeline must prove it can, on a known answer, before it is trusted on an
unknown one.
